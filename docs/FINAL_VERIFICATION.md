# 주문 흐름 검증 결과와 팀 인계 (2026-10-15)

## 추천 실패 복구: HTI 유지 검증

아래 기록은 앞선 상황 추천 보완 뒤 사용자가 화면에서 보고한 ‘감기 기운 → 졸림’ 추천 실패를 대상으로 한 후속 수정입니다. HTI 3.1·3.2·3.7~3.9·6.7·8.4.2와 ‘주문 진행 흐름’의 9단계 및 공통 규칙을 다시 읽고 기존 주문 엔진·가격 계산·화면 디자인을 유지했습니다.

### 수정 범위와 HTI 관계

- LLM이 필수 조건 칸에 넣은 추측을 그대로 신뢰하지 않습니다. 현재 사용자 입력에서 인용한 근거와 실제 메뉴 분류·수치·온도 등을 대조하고, 확인한 조건만 필터에 남깁니다. 실제 속성인 추론은 추천 순위에만 사용합니다.
- 검증한 제한만 `hard_constraints`로 누적합니다. 다음 발화에 일시적 추론이 필수 조건으로 넘어가지 않습니다. 기존 사용자 가격·카페인·우유 제외 제한과 ‘다른 추천’의 후보 제외는 유지합니다.
- 필수 조건 때문에 후보가 없거나 사용자가 지정한 속성을 확인할 수 없을 때는 조건을 바꿀지 한 번만 묻습니다. 주문을 비우거나 선택 전 메뉴를 담지 않습니다.
- **HTI 주문 단계 변경 없음.** 한 번에 하나만 묻는 공통 규칙에 맞춰 추천 조건을 재확인하는 동안 보류 온도 질문을 동시에 출력하지 않도록 했습니다. 보류·대기 주문은 그대로 있고, 온도 답을 하면 원래 주문을 이어 처리합니다.
- HTI 3.7의 우유 처리 기준은 앞서 사용자가 정한 ‘우유가 명시된 메뉴만 제외하고 빈칸은 확인 안내’ 방식을 유지합니다. 이번에 추가 변경하지 않았습니다.

- 두 번째 실제 요청에는 명시적 제한도 포함됩니다. 제한 없는 정확한 ‘나 좀 졸려. ㅋㅋ’ 문장의 최종 실제 응답과 브라우저 클릭은 이번에 별도로 검증하지 않았습니다. 해당 연결은 로컬 회귀 결과와 구분합니다. 데이터·임베딩·FAISS 인덱스는 변경하지 않았습니다.

## 상황·감정 추천 보완 검증

기존 LLM 호출 흐름 안에서 상황을 실제 메뉴 속성으로 해석하도록 보완했습니다. 감정별 메뉴를 고정하는 규칙은 추가하지 않았습니다. 추천 속성은 카탈로그에서 추출하며, 필수 조건 필터 뒤에 추론한 선호로 순위를 계산합니다. 대화 제어기의 추천 의도를 RAG에 전달하고, 기존 필수 조건은 현재 사용자가 명시적으로 바꾼 경우에만 갱신합니다.

외부 호출을 대체한 회귀 시험: API 58건, RAG 20건, 주문·상태 80건과 타입 검사 통과. RAG 시험에는 여섯 상황에 대한 후보 순위, 공감 응답, 가격·카페인·우유 제외·이전 후보 제외 유지, 보류 주문 유지, 단순 감정 공유, 실제 없는 추론 속성 제거, 필수 조건으로 후보가 없는 경우를 포함합니다. 모델의 대역 출력으로 수행한 시험을 실제 LLM 해석 결과로 간주하지 않습니다.

### 실제 호출 결과와 한계

추가 외부 호출 12회로 다음을 확인했습니다. 인덱스 재생성이나 실행 중인 사용자 서버·화면 변경은 하지 않았습니다.

- 상위 대화 LLM: 우울함·피로·입맛 없음·특별한 메뉴 희망·기쁜 기분·점심을 거른 상황의 여섯 발화를 메뉴 선택 맥락에서 `recommend`로 분류했습니다. ‘메뉴 추천은 괜찮고 기분 이야기만 한다’는 발화는 `information`으로 구분했습니다.
- 하위 RAG 계획 2건: 우울함·피로에서 실제 속성 선호는 생성했지만 `general`로 분류하는 문제와 일부 공감 문장에 효과를 암시하는 표현을 확인했습니다. 이후 상위 의도 힌트 전달·추천 분류 보정·효과 문구 차단을 추가했고 로컬 회귀 시험으로 확인했습니다.
- 전체 RAG 1건: ‘점심을 못 먹었어’에서 판매 메뉴 ID·근거·선택지는 정상 반환됐지만 달콤한 음료 위주로 추천해 식사 목적에 충분히 맞지 않았습니다. 이후 실제 샌드위치·브런치/디저트 속성 우선 해석 지침과 추론 상황의 선호 처리 방식을 보완했습니다.

**최종 보완 후 새로운 실제 API 호출과 브라우저 시험은 수행하지 않았습니다.** 따라서 여섯 발화의 상위 의도 분류 확인과 최종 추천 품질의 검증은 구분해야 합니다. 특히 끼니를 거른 상황의 음식 후보 우선 추천과 여러 턴의 실제 추천 품질은 후속 확인 대상입니다. 이번 결과를 모든 상황의 실제 추천 성공으로 기록하지 않습니다.

## 후속 수정: 채팅으로 모의 결제

“결제하기”가 결제 확인 단계에서도 주문 마무리로 돌아갈 수 있는 연결을 수정했습니다. 채팅의 명확한 결제 요청을 현재 단계에 맞춰 해석하고, `pay_confirm`에서는 결제 버튼과 같은 `pay_now`를 실행합니다. 매장/포장·보류 질문·결제 수단 선택을 건너뛰지 않습니다.

수정 후 외부 API 없이 Mock API 50건, 주문·상태 65건과 타입 검사·빌드가 통과했습니다. 실제 API 흐름 5건은 건너뛰었습니다. 이번 수정은 브라우저 표시·클릭 시험이나 실제 결제를 검증한 결과가 아닙니다.

## 후속 점검: 주문 버튼과 채팅 동작 일치

결제 요청과 같은 연결 누락이 있는지 확인하기 위해 주문 중·매장/포장·최종 확인·결제 수단·결제 확인·완료·온도 확인·수정 대상 확인·대량 수량 확인·전체 취소 확인의 10가지 상태에서 표시되는 주문 버튼 문구와 채팅 입력을 대조했습니다. 수정 전에는 “주문 마치기”, “네, 주문할게요”, “결제 수단 바꾸기”, “새 주문 시작”, “네, 맞아요”, “네, 비워 주세요” 등의 로컬 연결이 누락되어 있었습니다.

현재 단계의 버튼 문구 전체와 일치하면 해당 버튼 액션을 재사용합니다. “장바구니 보기”는 보류·대기 요청을 보존하고, 카드·간편결제의 명확한 단독 표현은 기존 결제 수단 선택으로 연결합니다. 서버에도 장바구니 확인·결제 수단 변경·새 주문 명령을 연결했습니다. 완료 후 새 주문은 이전 추천·조건·대화도 초기화하며, 진행 중인 주문을 동의 없이 지우지 않습니다. 복합 요청·질문은 단답으로 처리하지 않는 시험도 포함합니다.

외부 호출 없이 Mock API 53건, 주문·상태 79건이 통과했고 실제 API 흐름 5건은 건너뛰었습니다. 타입 검사·빌드도 통과했습니다. 실제 모델 해석과 브라우저 표시·클릭을 추가 검증한 결과는 아닙니다.

최초 실행에서는 명확한 주문을 LLM이 메뉴 선택으로 해석하는 경우와 브라우니 대안 ID 누락을 확인했습니다. `api/dialogue.py`는 명확한 주문·온도 답과 추가 주문·수량 변경에 기존 규칙을 재사용하고, `api/index.py`는 RAG 후보가 비었을 때 팀 대안 CSV를 사용합니다. 시험 코드의 가격 기대값도 실제 카탈로그 기준으로 바로잡았습니다. 수정 후 위 다섯 흐름이 통과했습니다.

초기 흐름 수정 단계의 회귀 검증: Mock API 42건, RAG 단위 3건, 주문·상태 55건 통과, 타입 검사와 빌드 통과. 실제 흐름 시험은 `tests/live-flow.test.ts`의 5건 통과입니다. 이는 `e64a91e` 후속 수정 전의 결과입니다. 이 파일은 기본 `npm test`에서 건너뛰며 별도로 실행할 때 실제 API를 호출합니다. 외부 API 사용료가 발생할 수 있습니다.

## 팀 리허설용 화면 확인표

아래 항목은 수동 시험 방법입니다. 미선택 상태는 아직 화면 통과 기록이 없다는 뜻이며, 문서 정리를 위해 시험을 다시 실행한 것은 아닙니다.

기존 8000·3000번 서버가 실행 중이면 먼저 종료합니다. 저장된 인덱스는 재생성하지 않습니다. 프로젝트 루트에서 터미널 두 개를 사용합니다.

```bash
source .venv/bin/activate
KIOSK_MODE=live RAG_REBUILD_INDEX=0 npm run api
```

```bash
npm run dev
```

접속 주소: `http://localhost:3000`. API 키 없이 Mock 화면을 보려면 첫 명령을 `KIOSK_MODE=mock npm run api`로 바꿉니다. Mock의 정보 답변·근거는 시험용입니다.

- [ ] 새 주문에서 `라떼 하나요` → `아이스요, 치즈케이크도 주세요`: 라떼 ICE 1개·케이크 1개·7,600원, 중복 없음.
- [ ] 새 주문에서 `라떼 하나랑 치즈케이크 하나요` → `카페인은요?` → `아이스요`: 정보 답변 뒤 온도를 다시 묻고 각 1개·7,600원.
- [ ] 새 주문에서 `브라우니 주세요` → 초코무스케이크 대안 버튼: 선택 전 0개, 선택 뒤 1개·4,200원.
- [ ] 새 주문에서 `아이스 아메리카노 두 잔이랑 치즈케이크 하나 주세요` → `아메리카노에 샷 하나 추가해 주세요` → `아메리카노 세 잔으로 바꿔 주세요` → `아메리카노 샷 추가는 빼 주세요`: 3잔·케이크 1개·11,700원.
- [ ] 새 주문에서 `아이스 아메리카노 하나 주세요` → `그게 다예요` → `포장이요` → `네, 그런데 치즈케이크도 추가요` → `네` → `카드로 할게요` → 결제 버튼: 변경된 6,700원을 다시 확인하고 모의 주문번호 표시.
- [ ] 라떼와 치즈케이크를 담은 뒤 `카페이능ㄴ요?` → `ice 요~`: 카페인 문의에 응답하고, 음료만 온도를 반영하며 중복 추가하지 않음. 이미 아이스면 그대로 유지.
- [ ] 새 주문에서 `음 아메리카노 2잔이랑 케이꾸`: 아메리카노 2잔을 유지하고 케이크 종류와 필요한 수량만 확인. 종류 선택 전 임의의 케이크나 다른 음료를 담지 않음.
- [ ] 새 주문에서 `아메리카노 두 잔 주세요` → 온도 질문 중 `샷 추가` → `3잔으로 변경해도` → `샷 제거 해줘 걍` → `아이스요`: 샷 없는 아이스 아메리카노 3잔·7,500원. 한 번만 담기고 같은 질문을 불필요하게 반복하지 않음.

위 항목은 초기 수동 시험표이며 일괄 완료로 표시하지 않습니다. 이번에 실제 확인한 입력 순서와 말풍선·버튼·메뉴 카드·주문 내역·완료 창의 결과는 문서 상단의 최신 점검 표를 기준으로 합니다.

## 알려진 한계와 팀 마무리

- 알려진 한계: 카페인 답변의 근거 ID가 비어 있습니다. 브라우니의 실제 RAG 대안 후보도 비어 팀 CSV 규칙으로 대체됐습니다. 이를 RAG 근거·대안 검증 성공으로 기록하지 않습니다.

- HTI·발표 담당: main 병합 시 `docs/HTI_키오스크.xlsx`와 `docs/HTI_키오스크.pdf` 원본을 보존했습니다. 팀 발표 자료·시연 캡처는 별도 취합이 필요합니다. 발표에는 실제 RAG 근거·대안 제한과 실제 화면에서 확인한 3개 흐름의 범위를 구분해 표시합니다.
